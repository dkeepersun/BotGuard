# 浏览器组件的混淆与加固：评估

状态：**评估结论，未实施**。日期：2026-10-29。对象：`packages/browser/src/`（npm 包 `@botguard/browser` 0.4.0）及 gateway 托管的副本 `internal/sdkassets/v1/`。

## 1. 问题

易盾的 SDK 做了“防逆向、防篡改、防调试”的加固。BotGuard 的组件是开源的，风险信号（`signals.js`）按明文 JSON 上报。要回答：

1. 构建期混淆对体积、加载和 PoW 计算有多大影响？
2. 混淆能挡住什么、挡不住什么？
3. 怎样与开源发布共存？
4. 按版本或按天轮换信号的字段名或编码，值不值得做？

## 2. 实测

### 2.1 方法

- 工具：javascript-obfuscator 4.2.2、esbuild 0.24.2；在 Chrome 156 无头模式下测，机器是 Apple M4 Pro。
- 构建方式：用 esbuild 把 `botguard.js`（含 `signals.js`、`solver.js`、`spawn.js`）、`signals.js`、`solver.js`、`worker.js` 各打成一个 ES 模块，再分四档：
  - **plain**：只打包；
  - **min**：压缩；
  - **light**：在 min 上做字符串数组（base64）和标识符改名，不做控制流平坦化；
  - **heavy**：在 min 上做字符串数组（rc4、两层包装、拆分字符串）、控制流平坦化 0.75、死代码注入 0.4、数字转表达式、对象键变换、自防御；不开 `debugProtection`，因为它会卡死打开开发者工具的真人。
- 性能测法：每个变体在全新的浏览器配置里加载 3 次，取中位数。测的是导入时间、风险信号采集时间、PoW 每秒哈希数（主线程跑 4 万次）和组件挂载时间。

### 2.2 体积

| 文件 | min（gzip） | light（gzip） | heavy（gzip） |
|---|---|---|---|
| `botguard.js`（主文件） | 18.5 KB | 33.3 KB（×1.8） | 151 KB（×8.2） |
| `signals.js` | 1.2 KB | 2.9 KB | 11.9 KB |
| `solver.js` + `worker.js` | 1.2 KB | 3.6 KB | 13.1 KB |

混淆本身很快：heavy 档整个 `botguard.js` 不到 0.5 秒，可以每次构建都重新混淆。

### 2.3 性能

| 指标 | min | light | heavy |
|---|---|---|---|
| PoW 哈希速度 | 45.6 万次/秒 | 41.9 万次/秒（−8%） | 33.1 万次/秒（−27%） |
| 导入 `botguard.js` | 6 ms | 7 ms | 23 ms |
| 采集一次风险信号 | 0.1 ms | 0.1 ms | 0.1 ms |
| 挂载组件 | 1–2 ms | 1 ms | 2 ms |

- PoW 是验证中最耗时的部分。heavy 档让每个真实用户的计算时间多约 37%，而 PoW 算法本身是公开的，攻击者用自己的原生实现计算，根本不受影响。
- 首次采集信号约 50–100 ms，主要花在 WebGL 探测上，各档差别在噪声范围内。
- 以上是桌面机器的数字。低端手机通常慢几倍，heavy 档的导入时间可能到 100 ms 量级（估计，没有实测）。

### 2.4 兼容性

- **组件测试**：用 min、light、heavy 三个构建分别替换源码，跑组件测试中与入口有关的 51 项（widget、i18n、kinds、slider、bind、selection、transport），全部通过。
- **严格 CSP**：在 `script-src 'self'`（不允许 `unsafe-eval`）的页面里，min 和 heavy 都能正常运行。产物里没有 `eval`、`Function(`、`debugger`。

### 2.5 反混淆尝试

用常见的自动反混淆工具 webcrack 2.15.1 处理 light 和 heavy 的产物，ES 模块和普通脚本两种形式都试过，都没有成功：报字符串解码函数未定义，自防御版本在沙箱里超时。看起来是工具没跟上这一版混淆器的输出格式。这能挡住只会用现成工具的人，但工具更新后就会失效；手工分析加运行时断点，几小时内就能读懂 light 档。

## 3. 混淆能挡住什么

先看攻击者实际怎么绕过组件：

| 攻击方式 | 需要读懂组件代码吗 | 混淆后 |
|---|---|---|
| 用 Puppeteer / Playwright 驱动真浏览器，加载真组件做题 | 不需要。信号来自浏览器环境，不来自读代码 | 没有作用 |
| 抓一次真实请求，改掉 `webdriver: true` 之类的字段后直接调用接口 | 不需要。请求体是明文 JSON，开发者工具的“网络”面板里就能看到全部字段 | 没有作用 |
| 想知道组件查了哪些特征，好逐项伪装 | 需要 | 增加成本：要么等反混淆工具跟上，要么手工分析几个小时 |
| 在页面里改组件的代码（比如让 `cdp` 恒为 false） | 需要定位代码 | 增加成本；自防御会让格式化后的代码失效，但可以绕过 |
| 自己实现 PoW | 不需要，算法写在 API 文档里 | 没有作用 |

结论：混淆只抬高“读懂检测逻辑”和“改组件代码”这两步的成本，而这两步不是绕过 BotGuard 的必经之路。真正挡住自动化的是服务端能观察到的事实：失败计数、网段、签发和提交的一致性、轨迹，以及被刷模式。

## 4. 与开源发布共存

- **源码照常公开**。检测逻辑写在仓库里，混淆只是让线上的产物难读，不构成秘密。文档已经按“浏览器信号都可以伪造”的前提设计（`docs/challenge-types.md` §5.3）。
- **只能对 gateway 托管的 `/sdk/v1/` 做**。npm 包的使用者要自己打包、排查问题，产物应当可读，否则 source map、报错堆栈和 webpack 4 的 legacy 构建都会变难用。
- **PoW 不混淆**：`solver.js`、`worker.js` 没有秘密，混淆只会拖慢真实用户（§2.3）。
- **完整性**：托管脚本由 gateway 自己提供，同源加载，不需要 SRI。如果业务方从 CDN 引用 npm 包，可以照常用 SRI；混淆不影响 SRI，只要每次发布重新计算哈希。

## 5. 按版本或按天轮换信号编码

做法：构建时（或 gateway 每天）生成一个编码模块，打乱字段名、字段顺序，加一层可逆变换（例如按密钥异或再 base64）。gateway 同时接受当前和上一个密钥，旧格式和明文直接视为没有信号（`NO_SIGNALS`，+40）。

收益：
- “抓包改字段再重放”的脚本每次轮换后都会失效，攻击者要重新提取编码规则；
- 与混淆配合时，提取编码规则要先读懂混淆后的代码。

代价：
- **npm 包拿不到轮换**。打包进业务网站的组件是静态的：要么永久接受它自带的固定编码，这等于不轮换；要么组件加载时从 gateway 动态加载编码模块，这要求业务页面的 CSP 允许 gateway 的脚本来源，部分网站做不到。
- **兼容性风险**：服务端要维护编码版本，部署和回滚都更复杂；一旦出错，所有用户都会被当成“没有信号”，统一要做题。
- **防不住真浏览器自动化**，它根本不需要伪造请求。

## 6. 建议

按收益从高到低：

1. **现在不做混淆，也不做信号编码轮换。** 成本已经实测清楚（体积 1.8–8 倍、PoW 慢 8–27%、发布和排错更复杂），而能挡住的两条路（读懂检测逻辑、改组件代码）不是绕过的必经之路。易盾的加固之所以有价值，是因为它和私有的检测模型、海量数据绑在一起；BotGuard 的检测逻辑本来就是公开的。
2. **先在线上观察信号是否被伪造。** 在管理后台按应用统计各信号的命中率和组合，例如“`webdriver` 为 false 但 `cdp` 为 true”、“信号齐全却从不出现 `pointer_moves`”这类矛盾组合。出现成规模的伪造，再考虑第 3、4 步。这一步成本低，还能给其他规则提供数据。
3. **如果第 2 步发现伪造，只对托管的 `signals.js` 做 light 档混淆**：gzip 增加约 1.7 KB，采集耗时不变；PoW 和 npm 包都不动。同时在构建时随机化字段名（和服务端共用一份映射表，每个版本换一次），抓包改字段的脚本每个版本就要重写一次。npm 包保持明文字段，服务端两种都接受。
4. **heavy 档和 `debugProtection` 不建议使用**：体积 8 倍、PoW 慢 27%，而且会干扰正常开发者。

## 7. 复现

测量脚本没有放进仓库。按 §2.1 的配置可以复现：

1. 用 esbuild 把 `packages/browser/src/*.js` 各打成 ES 模块，再用 javascript-obfuscator 按 §2.1 的两档参数处理（`target: 'browser'`、`sourceType: 'module'`、`seed: 1`）。
2. 测试时在 Node 中用 `--import` 设置 `globalThis.BOTGUARD_TEST_ENTRY` 指向产物，复用 `test/harness.mjs`。
3. 性能在 Chrome 无头模式里测：通过 CDP 打开一个导入各变体并计时的页面。
