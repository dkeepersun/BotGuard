# 旋转对齐验证（rotate）

状态：**已实现**。日期：2026-10-21。前置：`docs/challenge-types.md`（滑块）、`docs/click-challenges.md`（点选与随机出题）。

## 1. 玩法

图片中央有一块圆形区域被转歪了。用户拖动下方滑块，圆盘跟着旋转；把圆盘里的图案和外圈接上（线条连续、色块对齐）就松手。

```
┌──────────────────────────────┐
│      ╱     ┌────┐    ●       │
│    ╱      ( ↻ ╲  )   ●       │   外圈：完整图片
│  ╱         └────┘            │   圆盘：同一张图的中央部分，被转了 θ
└──────────────────────────────┘
 [→]━━━━━━━━━━━━━━━━━━━━━━━━━━   拖动距离 x ↦ 旋转角 x / 轨道长度 × 360°
```

## 2. 为什么这样设计

- **答案不靠“认出正方向”**。常见的旋转验证让用户把照片转正，大模型能分辨天空和地面，这类题已经快被攻破（COGNITION 2025：给例题后 AI 通过率 50%）。这里的图是程序生成的抽象画面，没有“正方向”：只能靠圆盘边缘与外圈的线条是否接上来判断。
- **复用滑块的拖动校验**。旋转角由拖动距离换算，所以提交的仍是“终点 x + 拖动轨迹”，服务端沿用滑块的轨迹规则（时长、点数、瞬移、等间隔、匀速、直线、终点一致），键盘方向键同样可用，并带 `KEYBOARD_INPUT`。
- **局限**：边缘连续性可以用图像算法沿圆周做模板匹配求出，专门写的脚本能攻破。与滑块、点选一样，它只是题型池里的一种，靠随机出题和风险分层提高针对性成本，不单独当作防线。

## 3. 生成（`internal/service/rotate`）

- 画布 320×200；圆盘半径 64–72 像素，圆心在中央附近随机偏移 ±12 像素。
- 画面：渐变底色 + 4–6 条穿过圆盘边界的粗色带（直线和弧线）+ 若干几何色块。保证每条色带都跨越圆周，用户才有对齐依据；外圈与圆盘之间留 2 像素浅色描边，避免缝隙泄露答案。
- 圆盘内容是同一画面的中央部分，预先旋转 θ（随机，排除 0°±30°，避免一眼可见或误碰）。外圈图的圆形区域用模糊的底色填充，不保留原图。
- 输出：外圈 JPEG（data URL）、圆盘 PNG（带透明，data URL）、圆心与半径、轨道长度（像素）。
- 正确的拖动距离 `x = (360 − θ) / 360 × track`，放进签名 challenge 的加密字段，浏览器看不到。

## 4. 协议（新增，向后兼容）

签发响应：

```json
{
  "kind": "rotate",
  "rotate": {
    "width": 320, "height": 200,
    "background": "data:image/jpeg;base64,...",
    "disc": "data:image/png;base64,...",
    "cx": 160, "cy": 100, "radius": 68,
    "track": 280
  }
}
```

solve 的 `answer` 与滑块相同：`{"x": 207.4, "trajectory": [[ms, x, y], ...]}`，`x` 为拖动距离（0–track）。服务端容差 ±7°（约 ±5.4 像素）。

## 5. 题型排序与配置

难度排序（`adaptive` 高风险时取最难的）：`click_shape` > `click_text` > `rotate` > `slider`。新建 action 默认包含全部四种题型；已有 action 不自动加入 rotate，需要在后台或命令行勾选。
