# 题型目录与第三期选型

状态：**第三期已实现**。日期：2026-10-21。前置文档：`docs/challenge-types.md`（滑块）、`docs/click-challenges.md`（点选）、`docs/rotate-challenge.md`（旋转）。

## 1. 调研来源

- **国内厂商的常见题型**：滑动拼图、文字点选、图标点选、语序点选、空间推理、推理拼图（交换两块）、九宫格、旋转。例如天翼云边缘安全支持“滑动拼图、文字点选、图形点选、VTT 空间语义”四种（[天翼云文档](https://ctyun.cn/document/10065985/10580095)）；行业资料对语序点选、空间推理的定义见 [阿里云开发者社区](https://developer.aliyun.com/article/1173230)。打码工具方面，点选、九宫格、空间推理被列为本地识别不稳定、需要走付费打码的题型（[少数派](https://sspai.com/post/97573)）。
- **研究结果**：
  - Open CaptchaWorld（NeurIPS 2025，[论文](https://arxiv.org/html/2505.24878)）测了 20 类题型。最强的智能体（Browser-Use + o3）总成功率 40%，人类 93.3%。o3 至少解出过一题的类型有：旋转匹配、图像识别、图像匹配、区域选择、飞镖计数、物体匹配、选动物；计数类（Dice_Count）、按顺序点击（Click_Order）、放点（Place_Dot）、路径（Path_Finder）都没有解出。
  - COGNITION（2025）的结论已写在 `docs/click-challenges.md`：大模型擅长“认出东西”，不擅长精确定位和数数。

## 3. 第三期四个新题型

所有题型都由程序生成，不依赖图片素材，避免版权和题库泄露的问题；答案都加密封存在签名 challenge 中，服务端无状态。

### 3.1 推理拼图 `jigsaw`

- 画面 320×200，切成 2 行 × 4 列共 8 块，随机交换其中两块。画面上有贯穿各块边界的色带和色块，错位的两块会让线条断开。
- 用户把一块拖到另一块上，两块互换。答案是这两块的编号（不分先后）和拖动轨迹。
- 校验：两块必须正确；轨迹从被拖的块内开始、在目标块内结束；拖动时长、点数、瞬移、匀速、等间隔规则与滑块一致。盲猜成功率 1/28。

### 3.2 图标点选 `click_icon`

- 提示是一条图标小图，例如“☁ ⚡ ♥”，要求按顺序点击大图中的同款图标。
- 大图中的图标经过随机旋转、缩放、换色，并混入其他图标作为干扰，所以模板匹配不能直接命中。
- 共 14 种程序绘制的图标：心、星、月、闪电、云、房子、水滴、箭头、十字、钥匙、雨伞、旗帜、叶子、圆环。

### 3.3 语序点选 `click_order`

- 图中散布一个四字成语的四个字，再加 1–2 个干扰字。提示只说“请按成语的正确顺序点击文字”，不给出顺序。
- 复用文字点选的字形图集和扰动方式；图集里补入成语用到的字，用 `tools/glyphatlas` 重新生成。

### 3.4 空间推理 `spatial`

- 图中按松散网格摆放带颜色的图形。提示例如“依次点击：红色圆形右边的图形、蓝色三角形上方的图形”，要求点的是被描述物体旁边的那个，而不是被描述的物体本身。
- 生成时保证答案唯一：被描述的物体按“颜色 + 形状”是唯一的，所指方向上紧邻的格子里恰好有一个图形。

## 4. 难度排序与配置

自适应模式在高风险时出列表中最难的题型。排序从易到难：

`slider` < `rotate` < `jigsaw` < `click_text` < `click_order` < `click_icon` < `click_shape` < `spatial`

- 新建 action 默认包含全部 8 种交互题型；已有 action 不会自动加入新题型，需要在后台勾选。（第四期起新建 action 不默认包含需要组件 0.3.0 的三种新题型，见 §7.5。）
- 题型列表的字段从 64 字符放宽到 255 字符（迁移 0006），8 种题型名连起来超过了 64 字符。

## 5. 局限

- 推理拼图：可以穷举 28 种交换组合，按“边缘接缝是否连续”打分来求解，与旋转题的局限同类。
- 图标点选、语序点选：专门训练过的检测模型可以识别。
- 空间推理：对通用大模型较难，但需要用户读懂一句描述，比点击类题目略慢。

所有题型都只是随机出题池中的一种，要配合风险分层、PoW 和限流一起使用。

## 6. 背景图（2026-10-28）

所有题型共用 `internal/service/imagegen` 的背景。原来的背景结构固定：两色渐变总是从左上到右下，上面叠 10–16 个半透明圆、矩形、三角形，再加均匀噪声。现在每张图随机组合以下几层，层的种类、数量、参数都随机：

| 层 | 做法 |
|---|---|
| 底色 | 任意角度的 2–3 段线性渐变、随机圆心的径向渐变、四角双线性混色，三选一 |
| 纹理 | 两层值噪声（fBm）：一层调亮度，一层向第三种颜色染色，尺度随机 |
| 图案 | 1–2 层淡的条纹、同心波纹、波浪线或网格，角度和周期随机 |
| 几何 | 8–14 个半透明的圆、旋转矩形、三角形、多边形、圆环，部分带渐隐 |
| 曲线 | 3–6 条细贝塞尔曲线 |
| 调色、颗粒 | 每个通道随机增益和 gamma（偏色），颗粒强度随机，三分之一的图是彩色颗粒 |

点选类（文字、语序、图标、图形、空间推理）另外加两步：

- **干扰笔画**（`imagegen.Clutter`，在题目元素之前画）：6–11 段短弧、钩形和 1–2 条长曲线，颜色与题目元素同类：文字题用深色，图形和图标题用鲜艳色。原来背景提亮后整体偏浅，题目元素是图中唯一的深色或高饱和区域，一个亮度或饱和度阈值就能把它们切出来交给 OCR 或模板匹配。干扰笔画都是开放的线条，不是字也不是封闭图形，真人一眼能分开。
- **成图扰动**（`imagegen.Finish`，在题目元素之后画）：1–2 条贯穿全图的淡细线、轻微偏色（每通道 ±5% 增益、±5 亮度）和颗粒。题目元素的颜色不再等于固定的调色板值，填充区域也不再是纯色。

滑块、旋转、推理拼图只换了背景，没有加这两步：干扰线会跨过缺口、圆盘边缘和图块接缝，反而给出“连续”的假线索，干扰真人判断。

### 实测

Apple M4 Pro，`go test -bench`，与改动前（main）对比：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 单张背景耗时 | 0.95 ms | 2.7 ms |
| 整题生成耗时（滑块 / 文字点选 / 图形点选） | 1.9 / 3.6 / 2.3 ms | 3.3 / 5.9 / 4.6 ms |
| JPEG 大小（base64，点选题 / 滑块背景） | 11–13 KB / 17 KB | 13–14 KB / 16 KB |
| 文字点选：远离文字的深色连通区域（亮度 < 110、≥ 12 像素，即二值化后 OCR 要排除的候选） | 每张 3.8 个 | 每张 10.8 个 |
| 空间推理：目标像素与固定调色板颜色相差 ±8 以内的比例（按颜色查表找目标） | 85.7% | 45.7% |
| 滑块：按缺口轮廓边缘强度找位置的求解器，第一名命中 / 前两名命中 | 37.7% / 100% | 42.7% / 100% |

- 耗时增加约 1.5–2.5 ms，仍在预生成题库（`PuzzlePool`）和并发上限能吸收的范围内；图片大小基本不变，因为新增的层大多是低频的。
- 滑块的数字说明背景对滑块帮助不大：假缺口才是主要防线，求解器总能找到真假两个缺口，再二选一。
- 没有做 OCR 和多模态模型的实测（本机没有 OCR 引擎），上面的连通区域数只是 OCR 前处理难度的代理指标。

## 7. 第四期新题型（2026-10-28）

选型经用户确认：时钟读数 `clock`、九宫格计数多选 `grid_count`、镜像辨别 `mirror`。不做五子棋、消消乐：极验自己的文档把它们和滑动拼图一起归为“防护能力有限、偏体验”的一类，识别出棋盘后穷举一步就能解，与推理拼图的局限重复。

### 7.1 时钟读数 `clock`

- **依据**：ClockBench（2025）用 180 个模拟时钟测试，人类读对 89.1%，最好的模型（Gemini 2.5 Pro）只有 13.3%，罗马数字表盘约 3%。模型读对时间之后，计算类追问基本都能答对，难点只在“看懂指针”。所以题目只考读表，不加计算。
- **画面**：320×200，4 个时钟（三分之一的题 5 个），半径 33–44 像素，互不重叠。表盘样式随机：12 个阿拉伯数字、只有 12/3/6/9、罗马数字 XII/III/VI/IX、只有刻度（12 点处是三角）；表盘底色、外圈和指针颜色随机，标有 12 点的表盘整体随机转动 ±12°。数字用内置的笔画字形画出，不需要字体文件。
- **提示**：“请依次点击：显示 3:40 的时钟、显示 8:15 的时钟”，2 个目标。
- **干扰钟**：优先放模型最容易混淆的时间：时针分针对调（3:40 → 8:20）、镜像（3:40 → 8:20，9:15 → 2:45）、差 5 或 10 分钟。
- **照顾真人**：时间都是 5 分钟的整数倍；两根指针至少相隔 24°，不会叠在一起；时针短而粗、分针长而细，指针不带尾巴（两针相对时尾巴会和另一根针重合）；两个目标时间至少相差 30 分钟，且互相不是对调或镜像，提示本身不会让人混淆。
- **校验**：沿用点选规则（`docs/click-challenges.md` §5），目标半径为表盘半径的 0.85 倍。
- **局限**：专门写的视觉程序可以检测圆、找指针、按长短区分时针分针，再按 12 点标记校正角度；表盘样式、转动和背景干扰提高了这类程序的编写成本，但挡不住认真投入的对手。少数不习惯看指针表的用户会慢一些，可以走“无法完成？”的备用路径。
- **性能**：Apple M4 Pro 单张约 4.7 ms（`go test -bench . ./internal/service/clock`）。

### 7.2 选格题框架

`grid_count` 和 `mirror` 是多选题：图片均分成 `rows × cols` 个格子，用户点格子选中或取消，选好后点“确认”。

- **盲猜率**：答案是任意非空子集，3×3 盲猜成功率约 1/511，2×4 约 1/255，远低于单选题和交换题（推理拼图 1/28）。
- **协议**：签发响应带 `grid`；`answer` 沿用点选格式，`clicks` 记录每一次点格子（包括取消），最多 24 次。服务端重放这些点击得出最后选中的格子，不信任浏览器自报的选择；再套用点选的读题时间、点击间隔、等间隔和鼠标移动规则（`click.Rhythm`）。
- **组件**：图片上叠一层格子，选中的格子加描边和对勾；“重置”清空选择和点击记录。不能用键盘完成，走“无法完成？”备用路径。

### 7.3 九宫格计数 `grid_count`

- **依据**：数数是多模态模型的短板。Open CaptchaWorld 里没有模型解出数骰子（Dice_Count），COGNITION 也把计数列为最难的一类。交互借用 reCAPTCHA / hCaptcha 的九宫格，用户最熟悉；以前不做九宫格是因为要真实照片和标注，这里内容全部程序生成。
- **画面**：3×3，每格 1–7 个半径 7.5–10 像素的小图形（圆形、三角形、正方形、五角星、十字），颜色随机，三角形、星形、十字随机转动，正方形只小角度倾斜（转到 45° 会被看成菱形）。每个图形都有深色描边，相邻图形之间留空，方便数清。
- **提示**：“请选出所有恰好有 4 个三角形的格子”，答案 2–4 格。非答案格三分之二是 N±1 个，粗略估计不够用。
- **性能**：单张约 5.7 ms。

### 7.4 镜像辨别 `mirror`

- **依据**：分清“翻转”和“转动”要做心理旋转。Mind's Eye（心理旋转、折纸）人类约 80%、模型低于 50%；MirrorQA（左右与镜像判断）最好的模型 65.4%、人类 99.3%。
- **画面**：2×4，每格是示例图形的一个副本，随机转动 ±75°、略微缩放、换色，其中 2–3 个被翻转。提示上方显示示例（正放）。
- **图形**：只用“长条加一个脚或凸起”的形状：L 五格、Y 五格、L 六格（5+1），随机取朝向和左右手。这类形状只要顺着长条走到脚，看它往哪边拐，就能判断。实现时先用 S、N、F、P 五格骨牌和随机六格骨牌试过，盲测里人自己都判断错（S 形转 90° 后看起来像它的镜像），已去掉；两臂长度接近的 L（4+3）也看不出哪条是长条，同样去掉。
- **局限**：形状种类少，专门训练的模型或“旋转匹配 + 是否需要翻转”的模板程序可以求解；它的价值在于通用模型的短板和多选的低盲猜率。
- **性能**：单张约 5.2 ms。

### 7.5 排序与配置

难度排序：`slider` < `rotate` < `jigsaw` < `click_text` < `click_order` < `click_icon` < `mirror` < `click_shape` < `clock` < `grid_count` < `spatial`。没有真实流量数据，先按研究结论排，`spatial` 仍是最难的。题型列表字段 255 字符，11 种题型名连起来约 100 字符。

**与旧版组件的兼容**：npm 安装的组件不会随 gateway 升级，0.3.0 之前的组件不认识这三种新题型，抽到就会验证失败。gateway 分不清旧组件和故意不报版本的脚本，如果“没报版本就不出新题型”，机器人省略字段就能永远避开它们，所以兼容放在后台把关：

- 新建 action（包括新应用自带的 login、`botguard-ctl action set` 不带 `-kinds`）默认只勾选任何版本组件都能显示的 8 种；三种新题型在后台标“新”，要手动勾选，旁边说明需要组件 0.3.0 及以上。已有 action 不变。
- 组件 0.3.0 起在签发请求里带 `widget` 版本号。gateway 对带浏览器信号的请求按版本计数（`widget:current` / `widget:outdated`；不带信号的直接调接口不算组件，不计入）。
- 应用的「验证策略」页在近 24 小时有旧组件请求时给出提醒和占比；含新题型的 action 标出“旧版组件会失败”。占比降到 0 再勾选新题型。gateway 托管的 `/sdk/v1/` 脚本随服务端升级，不受影响。

### 7.6 浏览器实测

用本地 gateway 和测试页，在内置浏览器里由我按真人方式操作：

- `clock`：第一次点击太快（两次点击间隔不到 150 ms），被 `TOO_FAST` 拒绝，规则按预期生效；放慢后按题目点中 10:20 和 6:05 两个钟，通过。该题的干扰钟里有 6:10（差 5 分钟）和对调读数。
- `grid_count`：逐格数清“5 个十字”，选中 2 格后确认，通过。
- `mirror`：第一版图形（含 S、N 等）我自己判断错，被 `SELECTION` 拒绝，据此收紧了图形集合；改后按“顺着长条看脚往哪拐”选中 3 格，一次通过。

未实测：真人在手机上操作；Safari、Firefox、微信内置浏览器。

## 8. 照片背景（2026-10-28）

参考易盾：所有题型都用真实风景照片做底图，照片本身的边缘、纹理和颜色就是干扰。BotGuard 改为照片与程序生成的图案并用，按应用配置（管理后台「背景图」，见 `docs/admin.md`）。

### 8.1 照片从哪来

- **内置**：57 张 Wikimedia Commons 上的 CC0（公有领域）风景照，约 20 类场景（高山草甸、秋林、海滩、城市远景、沙漠、花田、港口、湖泊、河谷、海岸、雪山、郁金香、村庄、瀑布、峡谷、薰衣草、梯田、灯塔等）。先在缩略图上剔除有人物、文字、全景畸变和绘画的图，再按全尺寸逐张复查，又去掉了 9 张远处有行人、登山者或招牌文字的。`tools/photolib` 按 `photos.json` 里的文件名重新下载，下载前通过 Commons API 确认许可是 CC0，非 CC0 直接报错；作者和来源页面由 API 返回后写回列表，不手填。存为 720×450、JPEG 质量 80，共 4.7 MB，gateway 和管理后台各增大约这么多。
- **自定义**：每个应用最多上传 50 张，存在数据库里。不公开的照片才是真正的“私有题库”。

### 8.2 每张题目怎样处理照片

照片库是有限的，而内置照片随源码公开，攻击者可以拿到全部原图。直接贴照片的话，用原图减去题目图就能得到缺口和文字的位置。所以每题都对照片做一遍处理（`imagegen.Source.Background`）：

1. 随机裁切照片宽度的 45–90%，随机镜像，转动 ±3°；
2. 平滑的随机扭曲，幅度 1.5–4 像素，一个整体变换对不齐全图；
3. 亮度、对比度、饱和度、色相（±12°）和各通道的偏色；
4. 40% 的题再叠一张别的照片（8–18% 透明度）；
5. 低频明暗起伏和颗粒噪声。

处理后再交给各题型画题目元素。各题型的区别：

- 滑块、推理拼图：直接用处理后的照片。推理拼图在照片上不再画色带，靠画面本身的连续性；为避免交换的两块都是天空或草地，会挑颜色相差足够大的两块（平均每通道差 ≥ 18）。
- 旋转：照片不提亮，色带从 3–4 条减到 2 条更细更淡的，不画圆弧。照片本身就是对齐的依据，但特写（如花丛）看不出哪边朝上，所以保留两条色带。
- 点选类（文字、语序、图标、图形、空间推理、时钟）和多选类：照片和程序背景一样先提亮，再画干扰笔画和题目元素。文字在细碎的照片（花丛）上对比度偏低，字形样式的改进放在下一步（字体描边、立体效果）。

### 8.3 实测

`BOTGUARD_ATTACK=1 go test -run SliderAttacks -v ./internal/service/imagegen`，每种背景 300 道滑块题，求解器只用浏览器拿到的图片和 `piece_y`：

| 背景 | 缺口在两个最暗位置之中 | 连续性求解器 | 图库比对求解器 |
|---|---|---|---|
| 程序生成 | 99.7% | 93.7% | — |
| 照片（处理后） | 80.3% | 75.3% | 86.7% |
| 照片（不处理，对照） | 82.7% | 75.3% | 93.3% |

- **连续性求解器**：找出缺口形状的两个最暗位置（真缺口和假缺口），比较拼块边缘的像素和缺口外一圈的背景，留下更连贯的那个。它在程序背景上达到 93.7%，远高于 `docs/challenge-types.md` 记录的“比较缺口边缘连贯性的简单求解器约 45%”。差别在于这里先用亮度找出两个候选，只在两者之间比较连贯性。也就是说，假缺口对认真写的求解器作用有限，**滑块的识别难度要在下一步单独加强**。
- **照片让滑块更难**：照片本身有大片阴影，缺口不再总是最暗的地方（99.7% → 80.3%），连续性求解器从 93.7% 降到 75.3%。
- **图库比对**：求解器持有照片库，并且直接被告知每张题目用的是哪张照片、哪个裁切区域（没有扭曲和调色）。这是上限：真实攻击者要先在 57 张图里搜索裁切位置和角度。它用题目图除以原图找出两个变暗的位置，再看哪个位置是原图被均匀压暗（真缺口），哪个里面是别处复制来的内容（假缺口）。不处理照片时成功率 93.3%，处理后降到 86.7%。处理能增加难度，但挡不住；照片库公开时，滑块的安全性不比程序背景好多少。
- **性能**：Apple M4 Pro，照片背景 4.3 ms，程序背景 2.7 ms（`go test -bench Background ./internal/service/imagegen`）。照片解码一次后缓存在内存（每张约 0.5 MB，内置库约 28 MB）。

### 8.4 建议与局限

- 默认“混合”：照片让多数通用求解器和多模态模型更难，程序背景每张都不重复，二者互补。
- 安全要求高的应用上传自己的照片（不要用网上能搜到的图），并取消内置照片。
- 没有测 OCR 和多模态模型在照片背景上的表现；点选类的效果只凭肉眼判断。
- 使用自己背景设置的应用不走预生成题库（题库只放默认设置的题目），每题现场生成，高峰时更容易触发降级。

## 9. 题面样式加强（2026-10-28）

参考易盾的题面：毛玻璃缺口、立体文字、半透明图标。全部在服务端完成，组件不用升级。

### 9.1 滑块

§8.3 的连续性求解器在程序背景上能达到 93.7%，假缺口作用有限。做了三处改动：

- **两种缺口样式随机出现**：凿刻（压暗，原样式）和毛玻璃（模糊后提亮，描边更亮）。真假缺口用同一种，求解器不能再只找“最暗的地方”。
- **缺口四周软化**：每个缺口（含假缺口）外侧 5 像素内，原图与模糊图六四混合并加噪声；拼块内侧边缘 5 像素同样软化，并略微提亮成玻璃边。求解器比对的正是缺口两侧紧挨着的细节，人看的是整体画面，这一圈的变化肉眼几乎看不出。
- 拼块形状的距离表按形状缓存，整题生成 4.4 ms（改动前 3.3 ms）。

实测：每种背景 300 题。求解器先找出与周围亮度差最大（变亮或变暗）的两个位置，再比较连续性，比较的位置在边缘处、往外 4 像素、往外 7 像素三种：

| 背景 | 求解器 | 改动前 | 改动后 |
|---|---|---|---|
| 程序生成 | 边缘处连续性 | 93.7% | 50.0% |
| | 往外 4 像素 | 92.7% | 63.7% |
| | 往外 7 像素 | — | 64.7% |
| 照片 | 边缘处连续性 | 77.3% | 60.0% |
| | 往外 4 像素 | 76.3% | 68.7% |
| | 往外 7 像素 | — | 66.0% |
| 照片 | 图库比对（已知裁切） | 89.0% | 76.3% |

最好的求解器仍有约三分之二的成功率。离边缘越远连续性越弱，这条信息是人判断时也要用的，消除不了，所以滑块仍然只是减速带。

### 9.2 文字点选、语序点选

每个字随机用三种样式之一：

- **深色字加浅色光晕**（原样式）；
- **立体字**：浅色或鲜艳的字面，后面是 3–5 层逐渐变暗的挤出，方向随机；
- **空心字**：浅色填充加深色描边。

40% 的字还会被 1–2 道细缝切断笔画，人读起来会自动补上，按连通区域切字的程序会把一个字切成几块。三种样式的颜色和明暗完全不同，一个亮度或颜色阈值不能同时切出所有字。照片背景的提亮从 35% 降到 20%，靠各样式自带的反差保证可读。

### 9.3 图标点选

照片背景上一半图标改为半透明白色加柔和阴影（易盾的样式），颜色来自背后的照片，按颜色找图标的方法失效；另一半仍是鲜艳色加深色描边。照片背景的提亮从 40% 降到 12%，让白色图标看得清。程序背景不变。

### 9.4 未做

- 叠字（易盾的“语序选词”）：属于新题型，按计划等前几阶段完成后再定。
- 没有 OCR 实测，文字样式的效果只凭肉眼和原理判断。
